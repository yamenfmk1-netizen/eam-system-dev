# نظام إدارة الأصول الكهربائية والصيانة

نظام حقيقي (وليس نموذج تصميم) لإدارة المباني والمعدات الكهربائية والاختبارات الدورية والصيانة والأعطال، مبني بـ **Next.js 14 + TypeScript + Tailwind CSS + Supabase**.

> **للنشر خطوة بخطوة من الصفر حتى رابط الموقع، استخدم `DEPLOYMENT_GUIDE.md`.**
> **لملخص ما تم تنفيذه وفحصه وما لم يُختبر فعليًا، راجع `FINAL_STATUS.md`.**
> **لتفاصيل كل إجراء أمني وكيفية اختباره، راجع `SECURITY_CHECKLIST.md`.**

## حالة التنفيذ

**المراحل الأولى والثانية والثالثة — مكتملة بالكامل ✅**

النظام الآن جاهز وظيفيًا بالكامل حسب المتطلبات الأصلية.
- إعداد Next.js + RTL + التصميم العربي
- سكيما قاعدة بيانات كاملة (كل الجداول المذكورة في المتطلبات) + RLS
- تسجيل الدخول والصلاحيات (4 أدوار)
- إدارة المباني (إضافة/تعديل/حذف/رفع صورة) + صفحة تفاصيل بتبويبات
- إدارة المعدات لكل الأنواع (12 نوعًا) + بيانات فنية تفصيلية للمولدات وATS وUPS والمحولات
- بيانات تجريبية لـ 11 مبنى ومعدات وأعطال واختبارات وصيانة

**المرحلة الثانية — مكتملة ✅**
- الاختبارات: تسجيل/تعديل، ربط بمبنى ومعدة، رفع تقرير PDF
- الصيانة: تسجيل وقائي/علاجي، صور قبل وبعد، قطع غيار مستخدمة
- الأعطال: بلاغ/تعديل/تغيير حالة، رفع صور، إغلاق تلقائي للتاريخ عند الحل
- قطع الغيار: إضافة/تعديل/حذف، تنبيه تلقائي عند بلوغ الحد الأدنى للمخزون
- الملفات والمخططات: رفع بكل التصنيفات المطلوبة (SLD, Layout, Manual...الخ)، عرض/تحميل/حذف
- تبويبات صفحة تفاصيل المبنى وتفاصيل المعدة أصبحت تعرض بيانات حقيقية من هذه الجداول

**المرحلة الثالثة — مكتملة ✅**
- لوحة تحكم برسوم بيانية حقيقية (توزيع حالة المعدات، الأعطال المفتوحة حسب الأولوية) ونسبة جاهزية محسوبة فعليًا من بيانات المعدات الحرجة
- التقارير: تصدير PDF وExcel لـ8 أنواع تقارير (المباني، المعدات، الاختبارات، الصيانة، الأعطال، قطع الغيار، الجاهزية، الصيانة القادمة خلال 30 يومًا)
- مركز التنبيهات: يحسب تلقائيًا المخزون المنخفض، الصيانة والاختبارات المستحقة خلال 7 أيام، والأعطال الحرجة المفتوحة
- البحث الشامل: شريط بحث فعلي في الأعلى يبحث لحظيًا عبر المباني والمعدات والأعطال وقطع الغيار
- سجل التعديلات: **تلقائي بالكامل** عبر SQL Triggers (`supabase/audit_triggers.sql`) — كل إضافة/تعديل/حذف على المباني والمعدات والاختبارات والصيانة والأعطال وقطع الغيار يُسجَّل مع القيم القديمة والجديدة
- إدارة المستخدمين: صفحة كاملة لإنشاء مستخدمين جدد وتغيير الأدوار وإيقاف/حذف الحسابات، عبر API route آمن يستخدم `service_role key` على الخادم فقط
- الإعدادات: تعديل البيانات الشخصية وتغيير كلمة المرور

> جداول قاعدة البيانات لكل هذه المراحل **موجودة بالكامل الآن** في `supabase/schema.sql`، بحيث يمكن بناء الواجهات عليها مباشرة دون أي تعديل على البنية.

## 1. التشغيل المحلي

### المتطلبات
- Node.js 18.18 أو أحدث
- حساب Supabase مجاني (https://supabase.com)

### الخطوات

```bash
# 1. تثبيت الحزم
npm install

# 2. نسخ ملف البيئة
cp .env.example .env.local
# ثم افتح .env.local وضع بيانات مشروع Supabase الخاص بك (الخطوة 2 أدناه)

# 3. تشغيل المشروع محليًا
npm run dev
```

الموقع سيعمل على `http://localhost:3000`

## 2. إعداد Supabase

1. أنشئ مشروعًا جديدًا على https://supabase.com
2. من **Project Settings → API** انسخ:
   - `Project URL` → ضعه في `NEXT_PUBLIC_SUPABASE_URL`
   - `anon public key` → ضعه في `NEXT_PUBLIC_SUPABASE_ANON_KEY`
   - `service_role key` (سري، لا يُستخدم في الواجهة) → `SUPABASE_SERVICE_ROLE_KEY`
3. من **SQL Editor** نفّذ ملف **`supabase/full_setup.sql`** كاملًا دفعة واحدة (يحتوي كل شيء بالترتيب الصحيح: الجداول، RLS، سجل التعديلات، تشديد الأمان، وبيانات تجريبية اختيارية في نهايته). التفاصيل الكاملة خطوة بخطوة في `DEPLOYMENT_GUIDE.md`.
   - إن كنت تفضّل التنفيذ الملفات منفصلة لتتبّع كل خطوة، الترتيب هو: `schema.sql` → `rls_policies.sql` → `audit_triggers.sql` → `security_hardening.sql` → `seed.sql` (اختياري).
4. من **Authentication → Providers** تأكد أن Email مفعّل
5. **إلزامي (أمان):** من **Authentication → Sign In / Providers → Email**، عطّل خيار **"Allow new users to sign up"** (أو ما يعادله في نسختك من Supabase). التطبيق لا يستدعي `supabase.auth.signUp()` في أي مكان أصلًا، لكن هذا الإعداد يمنع أي محاولة تسجيل مباشرة عبر Supabase REST API من خارج التطبيق. إنشاء الحسابات يتم حصرًا من صفحة "المستخدمون" بواسطة مدير النظام عبر `service_role key` على الخادم.
6. **إلزامي (أمان):** من **Authentication → Rate Limits**، فعّل الحدود المدمجة في Supabase لمحاولات الدخول وإعادة تعيين كلمة المرور كطبقة حماية إضافية فوق Rate Limiting المطبّق في التطبيق نفسه.
7. من **Authentication → Users → Add User** أنشئ حساب المدير التجريبي:
   - البريد: `admin@example.com`
   - كلمة المرور: اختر كلمة مرور قوية
   - في **User Metadata** أضف: `{"full_name": "مدير النظام", "role": "admin"}`
   - سيُنشئ Trigger تلقائي صف `profiles` المرتبط بهذا المستخدم
8. (اختياري) نفّذ `supabase/seed.sql` لإضافة بيانات المباني والمعدات التجريبية

### حساب المدير التجريبي
بعد إنشائه في الخطوة 7، سجّل الدخول به من صفحة `/login`.

## 3. النشر على Vercel

```bash
# ادفع المشروع إلى GitHub أولًا
git init
git add .
git commit -m "Initial commit"
git remote add origin <رابط المستودع على GitHub>
git push -u origin main
```

ثم:
1. اذهب إلى https://vercel.com → **Add New Project**
2. اختر المستودع من GitHub
3. في **Environment Variables** أضف:
   - `NEXT_PUBLIC_SUPABASE_URL`
   - `NEXT_PUBLIC_SUPABASE_ANON_KEY`
4. اضغط **Deploy**

Vercel سيبني وينشر المشروع تلقائيًا، وسيعطيك رابطًا مباشرًا (ويمكن ربط دومين خاص لاحقًا).

## 4. هيكل المشروع

```
app/
  login/                    صفحة تسجيل الدخول
  (dashboard)/              كل الصفحات المحمية (تتطلب تسجيل دخول)

    reports/ notifications/ users/ settings/ audit-log/

  layout/                   Sidebar, Header
  ui/                       StatusBadge, StatCard, ConfirmDialog
  buildings/                BuildingCard, BuildingForm
  equipment/                EquipmentForm
lib/
  supabase/                 client.ts (متصفح), server.ts (خادم), middleware.ts
  auth/permissions.ts       قواعد الصلاحيات المركزية
types/database.types.ts    كل الأنواع + تسميات عربية

  schema.sql                كل الجداول والعلاقات (17 جدولًا)
  rls_policies.sql          سياسات RLS + Storage buckets
  seed.sql                  بيانات تجريبية
middleware.ts               حماية المسارات + تحديث الجلسة
```

## 5. الأدوار والصلاحيات

| الدور | إضافة | تعديل | حذف مبنى | حذف عام | إدارة مستخدمين |
|---|---|---|---|---|---|
| مدير النظام (admin) | ✅ | ✅ | ✅ | ✅ | ✅ |
| مهندس (engineer) | ✅ | ✅ | ❌ | ✅ | ❌ |
| فني (technician) | ✅ | ✅ | ❌ | ❌ | ❌ |
| مشاهدة فقط (viewer) | ❌ | ❌ | ❌ | ❌ | ❌ |

الصلاحيات مطبّقة على مستويين: في الواجهة (`lib/auth/permissions.ts`) وفي قاعدة البيانات نفسها عبر RLS، بحيث لا يمكن تجاوزها حتى عبر استدعاء مباشر لـ API.

### الخطوة التالية

النظام مكتمل وظيفيًا. إذا رغبت بتوسعته لاحقًا (مثل: تصدير تقرير مبنى مفصّل بصورة PDF جاهزة للطباعة، أو ربط pg_cron لتوليد التنبيهات تلقائيًا يوميًا دون الحاجة لفتح الصفحة)، أرسل طلبك وسأبنيه بنفس النمط.

## 7. ملاحظة أمنية مهمة

- `SUPABASE_SERVICE_ROLE_KEY` يُستخدم فقط داخل مسارات API على الخادم (`app/api/users/...`) ولا يصل إطلاقًا إلى المتصفح — تأكد من عدم إضافة بادئة `NEXT_PUBLIC_` له أبدًا.
- عند النشر على Vercel، أضف `SUPABASE_SERVICE_ROLE_KEY` كمتغير بيئة **خاص بالخادم** (وليس Public) حتى تعمل صفحة "المستخدمون".
